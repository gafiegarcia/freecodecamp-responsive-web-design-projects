Overview

The B-Roll Marking Program (BMP) is a reasoning engine that converts unmarked YouTube review scripts into color-coded B-roll shotlists. It was developed by and for the Sobat HAPE tech review channel's videographer to automate the process of marking A-roll scripts to be transformed into B-roll shotlists with shooting angles color-coded meticulously — a process previously done manually, before every shoot.

BMP works by semantically analyzing a script's content, segmenting it into visual units, assigning product-specific tags, and applying color-coded verdicts that tell the videographer exactly what camera angle and shot complexity each segment requires.

The current stable release is BMP v2.1, production-ready since December 5, 2025. It supports three product types through external Tags Lists:

  • Smartphones — Tags List v2.5 (41 tags)
  • TWS / Earbuds — Tags List v1.1 (42 tags)
  • Tablets — Tags List v1.0 (51 tags)

BMP's architecture separates the universal verdict styling system from product-specific tag definitions. This means adding a new product type (e.g., smartwatches) only requires creating a new Tags List file — the core specification stays the same.

The Verdict System

Verdicts are the universal styling layer of BMP. Each verdict encodes two pieces of information into a single visual treatment: the color indicates camera angle, and the weight (bold or normal) indicates shot complexity.

There are seven verdicts. They are hard-coded — the videographer never has to guess what a color means:

Verdict System Table: Verdicts, Styling, and Meaning
Verdict Color (RGB) Bold Meaning
biru tipis rgb(0, 0, 255) No Eye-level static/slider solo indoor shots
biru tebel rgb(0, 0, 255) Yes Eye-level handheld shots; needs talent for lifestyle demo
ijo tipis rgb(56, 118, 29) No 45° static/slider solo indoor shots; angled close-ups
ijo tebel rgb(56, 118, 29) Yes 45°/over-the-shoulder handheld; needs talent for interactive demo
merah tipis rgb(255, 0, 0) No Top-down flat-lay solo shots
unmarked rgb(0, 0, 0) No A-roll, supers, photo samples — no B-roll needed
uncertain rgb(255, 0, 255) No Magenta fallback — no known tag fits; drives tags list evolution
Key principle: Verdicts are universal across all product types. Tags are product-specific. When BMP assigns a tag, the verdict is automatically determined by the Tags List — the engine does not "choose" a verdict.

About the naming

The verdict names use Indonesian terms: biru = blue, ijo = green, merah = red, tipis = thin (normal weight), tebel = thick (bold). It came from how the internal team at Sobat HAPE call the types of shot angles exactly how they mark it on Google Docs where they collaborate (which is the system that BMP is automating now). So ijo tebel literally means "bold green" — a 45° interactive shot requiring talent assistance.

Pipeline Architecture

BMP processes scripts through a strict 6-stage pipeline. Each stage must complete before the next begins. There are no shortcuts or stage-skipping.

  1. Initialize & Comprehend — Identify product type, load the correct Tags List, read the full script without processing it.
  2. Identify Visual Units — Segment the script into atomic shootable chunks while preserving semantic unity.
  3. Semantic Tagging — Assign one tag from the loaded Tags List to each visual unit.
  4. Apply Verdicts — Look up each tag's hard-coded verdict and apply the corresponding color and weight.
  5. Generate HTML Output — Produce an annotated artifact with styled visual units and diagnostics.
  6. Post-Processing — Analyze uncertain tags, propose new tags, and suggest Tags List refinements.

Stage 1 detail: Product type detection

The engine reads the script to infer the product type (smartphone, tablet, TWS, etc.), then loads the appropriate Tags List file. The loaded version is always the highest available (v2.5 > v2.4 > v1.11 and so on)

Critical rule: If the product type cannot be determined, or no Tags List exists for the detected type, BMP must halt immediately and request clarification. It never defaults to a product type.
Visual Units

A visual unit is the atomic building block of BMP output. It represents a single shootable segment in the script — the smallest meaningful piece of content that requires specific camera work. Every visual unit maps to exactly one tag and one verdict.

Segmentation principles (Stage 2: Identify Visual Units)

Visual units are identified based on semantic unity, not line breaks or paragraph boundaries:

  • Semantic Unity — Multiple sentences discussing the same shootable idea form one visual unit.
  • Concept Splitting — Different ideas in the same paragraph become separate visual units.
  • Granularity Limits — The minimum unit is a clause; the maximum is an entire paragraph. Never segment at word level.
  • Transitional Sentences — Merge with the following substantive content within the same paragraph.
  • Full Preservation — All text is preserved in the output. Nothing is discarded. Unmarked units get black text styling.

Examples

A single sentence covering one concept is one unit: 

// One visual unit → [tech_spec_soc → biru tipis]
"Chipsetnya pakai Snapdragon 8 Elite."

Multiple sentences about the same topic merge into one unit: 

// One visual unit → [charging_speed → ijo tipis]
"Support pengecasan sampai 100W Supercharge
dan 80W wireless. Buset, charger wireless 80W
aja saya belum punya."

But when a single sentence packs in distinct specs, it splits at clause level: 

// Three visual units from one sentence
"...beresolusi Full HD+, 2520 x 1080p,"      → [display_spec]
"refresh rate adaptif, 1-120Hz"              → [display_refresh_rate]
"dan brightness nya sampai 2600 nits."       → [display_brightness]
Tags Lists

Tags Lists are external Markdown files that define the product-specific vocabulary of BMP. Each tag within a list describes a shootable concept, includes reference trigger examples, and has a hard-coded verdict. The engine loads the correct list at Stage 1 and references it throughout processing.

You can access the latest version of the Tags List files here on my Notion, along with all documented previous versions.

File naming convention

BMP_Tags_List_{ProductType}_v{Major}.{Minor}.md

// Current production files:
BMP_Tags_List_Smartphone_v2.5.md   // 41 tags
BMP_Tags_List_TWS_v1.1.md          // 42 tags
BMP_Tags_List_Tablet_v1.0.md       // 51 tags

Tag anatomy

Every tag in a Tags List defines five properties:

Tags list properties and their purposes
Property Purpose
Tag name Unique identifier used during processing (e.g., camera_setup_spec)
Use case Describes what this tag represents visually
Trigger examples Common phrases for reference — not for keyword matching
Verdict Hard-coded color+weight from the Verdict System
Notes Shooting instructions and special handling rules

Product-specific differences

Each product type has unique tag categories that reflect how that product is reviewed and shot:

  • Smartphones have tags for fingerprint sensors, antenna systems, IP ratings, and reverse charging — none of which appear in tablet or TWS lists.
  • Tablets have 5 keyboard accessory tags and 4 stylus tags, plus display_surface for PaperMatte finishes — an entirely different shooting focus.
  • TWS/Earbuds have granular sound quality tags (bass, mid, treble), an ANC category with 4 tags, and no merah tipis (top-down) tags at all since flat-lay isn't part of the TWS shooting workflow.
Semantic Tagging Rules

Stage 3 (Semantic Tagging) is where BMP's intelligence lives. The fundamental rule is: understand the meaning, not the keywords.

Prohibited: Tagging based solely on keyword presence. Trigger examples in Tags Lists exist only as reference material to help understand a tag's purpose — they must never be used as pattern-matching rules.

Correct vs. incorrect tagging

Consider the script line: Kameranya jelek banget (The camera sucks).

  • ❌ Wrong: Keyword "kamera" detected → tag as camera_setup_spec
  • ✅ Correct: This is a subjective opinion about camera quality, no shootable visual → tag as subjective_opinion (unmarked)

Context-aware decisions

Several tags require contextual awareness beyond the visual unit itself:

  • intro_beauty_shot fires only once — on the first full product name mention. The context flag intro_beauty_shot_seen prevents duplicates.
  • camera_setup_spec triggers only when sensor/megapixel specs are introduced, not when discussing photo results (that's camera_result).
  • battery_endurance covers real-world usage experience ("tahan seharian"), while tech_spec_battery_capacity covers the raw mAh number.
  • ip_rating covers certifications and manufacturer claims, while durability_test covers the reviewer physically performing tests.
Output Format

BMP produces a single HTML file that preserves the full script in chronological order. Each visual unit is wrapped in a styled <div> with the appropriate color and weight applied via CSS classes.

HTML structure

<!-- Each visual unit follows this pattern -->
<div class="visual-unit {tag-name} {verdict-class}">
    {full text content of this visual unit}
    <span class="tag-label">
        [{tag} → {verdict}]
    </span>
</div>

<!-- Example: a chipset mention -->
<div class="visual-unit tech-spec-soc biru-tipis">
    Hape ini pake SoC Snapdragon 8 Elite.
    <span class="tag-label">
        [tech_spec_soc → biru tipis]
    </span>
</div>

File naming

Output files follow a strict naming convention derived from the input filename: 

// Pattern
BMPv2.1 {original-filename-without-extension}.html

// Examples
Input:  "Review iQoo Neo 10.docx"
Output: "BMPv2.1 Review iQoo Neo 10.html"

Input:  "Huawei_Pura_80_Ultra.docx"
Output: "BMPv2.1 Huawei Pura 80 Ultra.html"
Content labeling policy: Never add "Review" to a filename unless it already exists in the original. At Sobat HAPE, "Review" is reserved exclusively for organic content — paid collaborations should never use this term.

Diagnostics section

Every output includes a diagnostics block appended after the styled script. This section reports processing metadata for quality verification:

  • BMP version and Tags List version loaded
  • Total visual units processed
  • Tag distribution breakdown (count per tag)
  • Verdict distribution breakdown (count per verdict)
  • List of uncertain clauses (if any)
  • Keyword-only tagging check (always PASS or FAIL)
  • Overall processing status
Quality Standards

Before finalizing output, BMP verifies every run against a checklist of quality criteria. A run is considered successful when all of the following are met:

  • Product type successfully identified (no ambiguity)
  • Latest version of Tags List loaded and reported
  • Every visual unit has a tag and verdict assigned
  • intro_beauty_shot used exactly once
  • Zero keyword-only tagging violations detected
  • Full script preserved in chronological order
  • All verdict styling (color + bold) correctly applied
  • Diagnostics section complete and accurate

Success metrics

Metric Target
Uncertain rate < 10% of visual units
Output refinement time < 10 minutes for the user
Semantic grouping Clean, no split semantic units
Keyword-only violations Zero tolerance

A high uncertain rate (>10%) does not prevent output generation — it is a quality failure, not a critical failure. The output is still produced, with issues flagged in diagnostics for iteration.

Error Handling

BMP distinguishes between two failure categories, and they are handled very differently:

Critical failures (halt processing)

These prevent any output from being generated. The engine stops and requests user input:

  • Unknown product type — Script content is ambiguous or covers multiple product types.
  • Missing Tags List — Product type identified, but no Tags List file exists for it.
// Example error for missing Tags List
"Smartwatch detected, but no
BMP_Tags_List_Smartwatch file found.
Currently supported: smartphones, TWS, tablets."

Quality failures (proceed with flags)

These allow processing to complete, but issues are flagged in the diagnostics section:

  • High uncertain rate (>10%)
  • Potential keyword-only tagging detected
  • Ambiguous segmentation decisions

The rationale: the user needs the HTML output to iterate on. Halting over a quality issue would slow the workflow — better to deliver and flag, then fix in subsequent rounds.

Extending BMP

BMP is designed for extensibility through its separation of core specification and product-specific Tags Lists. Adding support for a new product type does not require changing the BMP version.

Adding a new product type

  1. Collect 3+ representative review scripts for the product type.
  2. Analyze shooting patterns and identify recurring visual concepts.
  3. Create BMP_Tags_List_{ProductType}_v1.0.md following the established table format.
  4. Validate against the collected scripts. Target <10% uncertain rate.
  5. Promote to production-ready status after validation.

Evolving an existing Tags List

Tags Lists version independently from the BMP specification. When updating:

  • Increment the version number ( v2.5 → v2.6 ).
  • Document all changes in the Version History section of the file.
  • BMP will automatically detect and load the highest version.

When the core spec changes

BMP version bumps only for architectural changes:

  • Patch (v2.1 → v2.2): Terminology fixes, clarifications, HTML styling tweaks.
  • Major (v2.1 → v3.0): New pipeline stages, verdict system changes, structural overhauls.

Verdict changes affect all product types universally, so they always trigger a major version bump.
